# Testing Glossary

| Term | Beginner explanation and portal example |
|---|---|
| SDLC | Software development life cycle: plan, design, build, test, release, maintain the portal. |
| STLC | Software testing life cycle: analyze requirements, plan tests, design cases/data, execute, report defects, close testing. |
| QA vs QC | QA improves the process; QC checks the product. Reviewing a test process is QA; running the benefits case is QC. |
| Error, defect, failure | A human error may create a code defect that causes a visible failure, such as wrong enrollment status. |
| Verification vs validation | Verification checks work against specs; validation checks that the product serves the employee's need. |
| Scenario vs test case | Scenario is broad (“check login”); case provides exact steps, input, and expected result. |
| Expected vs actual | Expected is the requirement outcome; actual is what the tester observed. |
| Smoke testing | A quick critical-path check, such as app opens, sign-in works, benefits load. |
| Sanity testing | A focused check after a small change, such as benefit date formatting. |
| Retesting | Repeat the failed case after a fix. |
| Regression testing | Check related existing behavior after a change, such as active enrollment and logout after a login fix. |
| Functional testing | Checks behavior/features, such as sign-in or case creation. |
| Non-functional testing | Checks qualities, such as mobile usability or accessibility. |
| Positive testing | Valid inputs produce expected behavior. |
| Negative testing | Invalid or unexpected input is handled clearly and safely. |
| Boundary-value analysis | Test at and near limits, such as maximum title length and one character over. |
| Equivalence partitioning | Group inputs expected to behave alike, then sample each group (valid, malformed, empty email). |
| Severity vs priority | Severity is impact; priority is urgency to fix. |
| Test plan | Scope, approach, resources, environment, and exit conditions for a test effort. |
| Test data | Inputs prepared for testing, such as fictional inactive employee EMP-1002. |
| Test environment | Browser, operating system, app build, and setup where testing occurs. |
| Entry/exit criteria | Conditions to start a phase and conditions to consider it complete. |
| Defect life cycle | A defect may be open, assigned, fixed, retested, closed, or reopened. |
